# 三端前端与调用契约：用户可见差异

对比范围：`452e7d7 → 74f209d`，以这两个 Git 版本为准。本轮只读核对代码并补充交接文档，没有重跑浏览器验收、调用设备或访问公司服务。后续正在补的 `/start` 会话竞态修复不计入本次对比。

**主要页面和操作顺序保留，但不能承诺完全无感。** 老用户仍然创建配置、探查下发、启动、停止、删除和换 Agent；现在会明确看到首次绑定尚未确认、冲突操作被拒绝、具体失败原因，以及换 Agent 的新 ID 和空白数据含义。

## 1. 哪些没有改变

- 仍然是原“虚拟机”页面中的 Android、鸿蒙、iOS 三个页签，左侧创建配置、右侧实例卡片；路由和页签容器没有改。
- 创建仍然只建立后台配置；现有机型/系统/资源输入、平台目录入口和创建请求字段没有改。
- 正常已停止实例仍可启动；运行中的实例仍可停止；停止保留实例与数据；复制配置仍需新别名、不会复制实例数据。
- 原有“探查 → 候选 Agent → 下发”路径保留，没有新增绑定向导，也不要求用户填写端口、租约、UDID 或新的操作编号。
- 基础状态文字保留：未下发、启动中、运行中、停止中、已停止、异常、不可用、待恢复；Android 原有“下发中”也保留。
- 页面仍然约每 3 秒更新列表；更新只是读取本次结果，不会自动再次提交启动、停止、删除或换机。
- 设备总览的组件、空闲/未就绪/占用中显示规则以及前端设备控制调用封装没有改；服务端提供的健康与占用事实更严格。

## 2. 实际可见的变化

| 场景 | 基线行为 | `74f209d` 的用户体验 |
| --- | --- | --- |
| 首次下发 | 下发过程中就可能显示已分配的 Agent，失败也容易留下“已绑定”的观感。 | 成功回报前只显示“启动中 / 绑定中：目标 Agent”；只有本次启动成功确认后才显示正式绑定。 |
| 首次绑定失败 | 已分配、启动失败与是否可以重新下发的关系不够明确。 | 配置保留为异常、显示未分配和错误原因，可重新探查或删除；不会自动再启动。 |
| 启动中点击停止 | 三端原页面都允许在 `starting` 时点停止。 | 启动中不再提供停止等冲突操作；停止中也不能继续提交相冲突的操作。 |
| 复制配置 | 原来随时可以打开复制弹窗。 | 启停或请求进行中禁用复制；弹窗打开后源实例发生变化，也会拒绝继续复制。运行中和普通已停止状态仍可复制。 |
| 已绑定实例异常后再启动 | Android/iOS 原来只看异常等状态就允许启动；鸿蒙另有旧占用限制。 | 未确认原实例已停止时不提供“启动”，显示停止提示与“重试停止”；删除、换 Agent 按舍弃旧配置的例外规则处理。 |
| 一次操作占用按钮 | 原来主要只禁用正在点击的同一个按钮，多个实例共用一个忙碌标记。 | 同一实例本次请求期间禁用其他动作；另一台实例的请求不会清掉它的忙碌状态。 |
| 换 Agent 确认 | 原候选下发没有统一的破坏性操作确认。 | 三端统一确认“删除原配置、目标 Agent 新建空白机器、原数据不迁移”；Android/鸿蒙候选按钮也明确显示“换到这台”，iOS 原本已有该按钮文字。 |
| 换机结果 | 基线三端已经采用删旧 ID、新建 ID；并非本轮才引入新 ID。 | 页面直接用响应中的新实例替换旧行；旧 Agent 离线不阻塞换机，新实例只尝试启动一次，失败显示在新配置上，旧配置不会自动回来。 |
| 删除结果 | 原来主要等下一次列表查询才能看到配置消失；鸿蒙旧占用还可能挡住普通删除入口。 | 删除成功响应立即移除后台行；没有“待清理/重试清理”页面流程，鸿蒙也不再要求先人工释放旧占用。 |
| 失败原因 | Android 原卡片不显示 `error_message`，自动刷新还会清掉页面顶部错误；另外两端把错误放在卡片字段中。 | 三端统一在操作区下方显示具体错误与必要说明；后台定时刷新不抹掉操作错误。`agent_offline` 仍不铺红色错误，另显示实例状态暂不可确认。 |
| 探查与刷新 | 较早的响应可能覆盖当前选择或较新的实例状态。 | 收起候选面板后旧结果失效；A 的探查不会显示到 B；旧“已停止”列表不能把新“启动中”盖回去；慢列表请求不会被定时器不断堆积。 |
| 启动阶段文字 | 某些内部阶段没有对应中文。 | `probing` 显示探查中；`creating/connecting_hdc/checking_driver` 统一显示启动中，不把底层通道阶段直接交给用户。 |
| 鸿蒙额外内容 | 有人工释放旧占用弹窗及 GUI/Headless/Linux 路线说明。 | 移除常规人工释放入口和路线说明；机型、系统与执行资源配置区保留。 |

**两个必须讲清楚的结果：** “下发成功 / `sent:true`”仅表示本次命令已发出，不能等同已运行；“`switched:true`”表示旧配置已退役、新配置已建立，也不能等同新机器已启动成功。名称可以沿用，VM ID 必须按新实例更新。

## 3. 按钮看得到，但仍可能收到 409

页面按钮先根据当前 VM 状态判断；服务器还会核对最新状态、归属和实际占用，所以按钮可见不等于服务器必定接受。

| 冲突 | 用户看到的结果与处理 |
| --- | --- |
| 另一个用户或请求已开始启停 | 409：“实例正在操作中，请等待本次结果”；不会把第二个动作排成后台队列。 |
| 设备正在执行、安装或观看 | 409：设备正在执行任务、安装或观看；先结束对应使用，再重新发起本次操作。 |
| 原实例未确认停止 | 409：尚未确认停止；不能为了再次启动而偷偷覆盖或重建原实例。 |
| Agent 标识对应的宿主发生变化 | 409：归属尚未确认，禁止在另一台宿主执行原实例操作。 |
| 首次启动发现不能自动接管的既有数据 | 409：本次未创建该宿主实例，不能自动接管；应使用新配置。 |

直接调用 API 的脚本也会受到保护：例如基线 iOS 删除接口没有像其他两端一样拦截运行态，现在统一检查；绕过页面不能绕过 409。

即使 HTTP 返回成功状态，也要读响应中的 `sent` 与 `instance.state`：发送失败可以直接返回 `sent:false + error` 实例；启动、停止的执行失败或超时也会作为本次失败显示，而不是无限留在中间态。

离线删除、离线换 Agent 是明确例外：只退役旧后台配置，不等待离线宿主的执行锁或观看连接；在线宿主上的真实任务/观看占用仍会保护，不能以“删除”绕过。

## 4. HTTP 路径和请求 payload 是否变了

本仓库两个版本均没有 `web/src/api/client`；实际封装是 **`web/src/lib/api.js`**。这个文件两版的 Git blob 完全相同：`85e9d1fabcdd96393851435f9d9b704f74366a5d`。因此以下前端 HTTP 地址、请求参数、鉴权方式均未变化。

| 平台 | 实例接口前缀 |
| --- | --- |
| Android | `/api/internal/vm/instances` |
| 鸿蒙 | `/api/internal/harmony-vm/instances` |
| iOS 模拟器 | `/api/internal/ios-sim/instances` |

| 操作 | 原有调用，仍然使用 |
| --- | --- |
| 列表 / 创建 | `GET 前缀` / `POST 前缀`，创建字段仍由原平台表单提交。 |
| 修改 / 删除 | `PATCH 前缀/{id}` / `DELETE 前缀/{id}`；删除无请求体。 |
| 探查 | `POST 前缀/{id}/dispatch-candidates`，无请求体。 |
| 首绑或换 Agent | `POST 前缀/{id}/dispatch`，请求体仍只有 `{ "agent_id": "目标 Agent" }`。 |
| 启动 / 停止 | `POST 前缀/{id}/start` / `POST 前缀/{id}/stop`，无请求体。 |
| 复制配置 | Android/鸿蒙仍由页面组装原配置发创建；iOS 仍使用 `POST 前缀/{id}/copy`，没有强行统一。 |
| 内部鉴权 | 仍为原 Bearer token 读取和 `internalHeaders()`，没有新增前端鉴权步骤。 |

**请求兼容不等于响应含义没变。** 调用方需要注意：

- 首次下发期间 `assigned_agent_id` 为空，目标在 Android/鸿蒙的 `runtime.operation.target_agent_id` 或 iOS 的 `runtime_state.operation.target_agent_id`；运行成功确认后才成为正式绑定。
- 失败信息仍使用 `error_message`；新增的 operation 信息记录本次 pending/outcome 等事实，不能用它触发调用方的自动重试。
- 删除的 `deleted:true` 表示后台配置已经删除；`cleanup_sent/avd_cleanup_sent` 只是清理命令是否发送，**不是宿主实例已删干净的确认**。离线宿主的旧实例仍可能等到对账时才清掉。
- 换机响应仍有 `switched:true、old_vm_id、instance`；`instance.id` 是新 ID，状态可能是 `starting` 或 `error`；无需依赖另一个 `new_vm_id` 字段。
- 删除响应现在三端补齐了 `alias_deleted/cleanup_sent/avd_cleanup_sent`；旧鸿蒙删除响应的 `quarantined_port` 不再返回，脚本不能继续依赖它。
- 页面会立即应用响应中的实例/删除结果，再读取列表；HTTP 接口没有变成等待整个原生启动完成才返回的长请求。

这里比较的是 Web 调用 Server 的 HTTP 契约；Server 下发给 Agent 的操作编号、宿主标识、原生超时等字段属于另一层，不能混称为“前端 payload 改了”。

## 5. “运行中、就绪、占用中”不是同一个意思

| 名称 | 它回答什么 | 不能据此推断什么 |
| --- | --- | --- |
| VM 页“运行中” | 生命周期账记录实例已运行；首次绑定需要本次成功回报，之后也可能由对账更新事实。 | 不能保证当前控制通道仍健康、设备空闲或某条业务用例已经通过。 |
| `readiness.ready=true` / 总览“空闲” | 控制链路已有有效健康结果；总览“空闲”还要求设备在线且没有锁占用。 | `ready` 单独为 true 不代表无人使用，也不等于业务执行成功。 |
| 总览“占用中” / `effective_status=busy` | 在线设备持有执行/控制锁。 | VM 可以同时处于运行中，甚至健康，但不能再接新的互斥操作。 |
| VM 按钮正在“探查中/启动中…” | 本页面正在提交或观察某次生命周期操作；`busyByVm` 是逐行请求保护。 | 它不是设备总览的执行占用状态；状态徽章的 CSS 类 `busy` 也不是设备锁。 |

设备总览组件没有更换。本轮服务端增加“旧健康结果过期”和“生命周期操作期间不可用”的保护，因此原来可能误显示空闲的设备，现在会显示未就绪。当前总览原因映射尚未专门翻译新增的 `probe_stale/vm_maintenance` 小标签，可能显示这个原因码及其中文说明；这也是实际可见差异，不能说所有提示都没有变化。观看订阅也可阻止停机，即使总览没有显示锁占用；用户应结束观看后再操作。

## 6. 鸿蒙移除人工 force-release 后怎么操作

1. **要保留这台机器：** 正常停止；失败时查看原因，原 Agent 可用后再次明确发起停止，确认停止后再启动，不再填写人工释放确认和核验记录。
2. **要丢弃旧机器：** 非运行、非启停中的配置可直接删除，或探查后换到其他 Agent；后台旧 ID 立即退役，换机生成新 ID 并启动一次，数据不迁移。
3. **正在启停或在线使用中：** 仍需本次操作结束、结束任务/安装/观看；没有人工按钮可以绕过保护。

`internal.harmonyVms.forceRelease()` 封装和 `/force-release` 路由仍为兼容保留，但普通页面不再调用；服务端对仍有关联 Agent、租约或 HDC 资源的实例返回 409，人工勾选和填写字符串不再能替代实际清理证据。
