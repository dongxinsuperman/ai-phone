## One AVD, five snapshot generations

1. Create one API33 AVD through the actual local Server/Agent using `save`; record the guest kernel boot ID and create bounded sleep marker A; stop normally and require nonempty `default_boot/snapshot.pb` and `ram.bin`.
2. Start the same AVD with `save`; require the same boot ID and A's exact PID/starttick/cmdline; stop to save it again.
3. While stopped, PATCH the existing config to `discard_changes`; start and verify A; create bounded sleep B; stop without saving.
4. Start again with `discard_changes`; require the original boot ID and A, but reject B's exact signature; stop.
5. While stopped, PATCH to `cold_boot`; start and require a different boot ID with neither original marker; stop.

Markers are `/system/bin/sleep 1131` and `1133` with inherited ignored HUP and closed ADB pipes. They require no App or additional root operation, create no guest files, and expire without signals. The test adds no fixture or global sync: actual product provisioning and normal stop still execute unchanged. Guest reads reject unknown/partial `/proc` evidence instead of treating read errors as absence. A reused PID alone cannot prove restoration. The normal matrix has a 900-second budget, shorter than either marker lifetime.

Each start/stop must succeed under its own exact Server operation request ID and action. Native launch argv must name only this VM at private port 5666 and use the correct snapshot flags, with no wipe. Full native logs, incremental log ranges, snapshot metadata and AVD identities are saved at every generation. Acceptance requires real kernel/process restoration; the presence of snapshot files or log text alone is insufficient.

## Existing-image negative phase and explicit restoration

Read-only SDK package metadata currently confirms installed API34 Google APIs ARM64 revision 14. After generation five is stopped, save the complete Server configuration and SHA-256/inode/size/mtime of every regular file in the exact owned AVD (bounded to 2,000 entries and 32 GiB; no symlinks). PATCH only `system_image` to that installed API34 package and issue one start. Acceptance requires this exact operation to finish failed with the actual API33/API34 identity-mismatch error, zero additional native launches, no active runtime, and byte-identical original AVD contents. A missing image, unrelated failure, timeout, wrong request ID, or physical stopped state cannot pass this check.

Then explicitly PATCH the original image value back and issue a separate new start. This sixth actual generation retains `cold_boot`, the same VM/AVD, and must report actual API33 with a new boot ID and no old RAM markers. Stop and delete this exact VM. This is an explicit configuration restoration after a proved failed attempt, not a retry loop. If installed API34 metadata is absent, report this phase as not covered; never count missing SDK as image-guard acceptance.

## Isolation and failure handling

Fresh loopback Server/WS, random token, SQLite/storage, private AVD/user/runtime directories, private ADB port 15037 with a nonexistent USB selector, and the exact owned serial are required. The global CLI/profile, default Agent provider and orphan/reclaim scans are not invoked. Capability and VM handlers accept only the sole VM ID returned by the new local Server. The Manager observer delegates the original arguments, deadlines and results unchanged.

Successful execution requires one native AVD creation, the five policies above (plus the explicit restoration generation when covered), immediate Server ledger removal, native AVD/ini removal, no owned processes/runtimes, private ADB exit, released emulator ports, unchanged protected metadata and matching product/harness hashes. A failed run preserves its AVD. A failed or unresolved stop of the current generation cannot be repeated in cleanup; a later restarted generation may receive one protective stop. Already dispatched handlers are allowed to settle without cancellation or redispatch before resource cleanup; unresolved work is reported and its resource scope retained.

This covers snapshot policy and existing-image identity. It does not re-prove App localStorage persistence, external guest networking, VLM/business execution or physical-device behavior.
