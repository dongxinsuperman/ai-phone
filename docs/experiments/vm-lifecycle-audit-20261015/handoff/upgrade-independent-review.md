# 升级安全独立审查

审查日期：2026-10-16（Asia/Shanghai）。初审版本：`74f209dc6556d4678291b0dce63a9817741b6bea`，产品代码提交 `0e9bde8`；旧版本对照：`452e7d77326f9fc0e5b003ecbf6cec5fc499e4bf`。

**结论：不能把 74f209d 描述为“存量升级、混合版本与回滚均无感安全”。** 初审发现的安装身份冲突误删和普通启动误走换机，已在后续 Server 升级安全补丁中修正，并通过下述 54 项隔离复验；旧 Server 的升级顺序风险仍由部署前提约束。可以交接的是“带前提的数据保护与明确冲突”，不是任意顺序、任意目录、运行中无中断升级。

修后验收时 HEAD 仍为 74f209d，补丁尚未统一提交；本次实际检查的产品与测试文件 SHA256 固定在 [代码快照](upgrade-independent-code-snapshot.json)。该补丁已包含在 `d7cbac0`；整体最终交付 `2dc9844` 还包含后续原生端口、停止预算、Android 同步屏障、镜像核验和已有数据容量修复，见[主交接指南](../../../vm-lifecycle-upgrade-guide.md)，不能只部署 74f209d。此前个人三端原生验收的事实仍成立，但不是旧版本存量升级验收。

本审查只读取本地代码和已保存证据，使用独立 SQLite、临时身份目录和 Fake Hub；未连接实际 Agent、未执行 ADB/HDC/simctl/Emulator、未访问公司服务。专属测试文件为 [test_vm_upgrade_independent_review.py](../../../../backend/tests/test_vm_upgrade_independent_review.py)。

## 1. 需要明确处理的风险

| 编号 | 结论及触发条件 | 证据与处理状态 |
| --- | --- | --- |
| U1 / P1，已修 | **同一电脑更换或丢失 Agent storage 身份，会被误当作另一台宿主并收到删除指令。** `agent-host-id` 是安装目录中的随机身份，不是物理电脑指纹。Android/iOS 在新目录启动 Agent 后仍能发现原来的 AVD/UDID；鸿蒙若迁移了 registry 却漏迁该身份文件，也会报告原实例。74f209d 将新身份判为 foreign copy 并下发删除。 | 三端、原 owner 在线/离线共 6 个安全断言在初审均失败，见 [初审日志](upgrade-independent-baseline.log)；修后 6 项均通过。证实的是“原来发删除、修后不发删除”，没有实际删除设备。现在总账存在但身份冲突时，不自动删除、不接管，保留原账并在 Server 日志记录冲突；总账不存在仍按既有规则清孤儿。 |
| U2 / P1 | **先升级或重启 iOS Agent、仍连接旧 Server 452e7d7，停止实例可能被误删。** 旧 Server 按新 session 查询 `known_ids`，随后认领停止实例，却继续用认领前的集合计算 orphan，最终对刚认领的实例发送 delete。 | 从 Git 提取旧版真实 `handle_vm_reconcile` 函数，在隔离数据库中重放；数据库仍有该配置且 owner 已改为新 session，同时 Fake Hub 收到同 ID 的删除指令。见 [单用例详细日志](upgrade-legacy-server-order.log)。这是旧代码固有问题，本次升级会触发；禁止 Agent-first 连回该旧 Server。 |
| U3 / P1，已修 | **普通 `/start` 与同宿主重新认领交错，可能误走“换 Agent”，退役旧 ID。** `/start` 在锁外取得旧 session，锁内读取时归属已改为新 session，若把两者不相等直接当显式换机，就会删除旧账/数据。 | 普通启动现在显式传 `allow_switch=False`；三端均在冲突时返回 409，要求刷新后再启动，原 ID、原生身份和状态保留，不发 DELETE/START。本审查运行了 [三端竞态回归](../../../../backend/tests/test_vm_upgrade_compat_audit.py)，均通过。 |
| U4 / P2，兼容边界 | **旧 Agent 的停止清单不能认证新规则需要的事实。** 74f209d 下旧 Android/iOS Agent 缺少 `host_id`、`instance_proofs`，新 session 无法认回老停止实例；后续补丁进一步要求三端 `inventory_complete is True` 才认证停止/缺失。旧鸿蒙虽已有实例名和 `managed_instance_present`，仍缺此完整性标记。 | 专属测试按 452e7d7 实际消息结构重放；修后三端均保留旧账、不给缺少完整性标记的清单盖“已停止”章。连旧 session 未改变的情景也已覆盖。数据不因此删除，但可能保持 `agent_offline`，必须完成 Agent 升级，不能宣称所有旧 Agent 都兼容。 |
| U5 / P2 | **仅把 Agent 降回旧版，不等于可用回滚。** 一旦数据库已记录 `owner_host_id`，旧 Agent 的新 session 没有对应 host 身份，不能恢复这批归属。 | 三端隔离重放均保留旧 owner、保持离线且不发送删除。需要版本配对与恢复方案，不能承诺单独降级 Agent 后自动可用。 |
| U6 / 数据恢复前提 | **恢复较旧数据库快照会让较新原生实例成为 orphan。** 这符合“Server 总账无 ID 就清理”的既定规则，不是代码回滚的同义词。 | 对账清单报告数据库没有的 ID，三端均下发精确删除。专属测试明确演示这一结果。禁止把旧 DB 快照恢复到仍连接着较新实例的 Agent 群上。 |

U1 的安全边界不能只限定为“原 owner 离线才不删”：同一电脑同时运行旧 Agent 与使用新 storage 的 Agent 时，两者仍可能看到**同一份**磁盘实例。两个安装身份都在线，不能证明存在两份可独立删除的实例。

## 2. 哪些情况下已有代码证据支持数据保留

以下均有条件，不能省略右栏前提。

| 可以支持的判断 | 必要前提 |
| --- | --- |
| 新 Agent 可以认回没有 `owner_host_id` 的旧停止配置，并写入新持久身份。 | 旧 session 已离线；Agent 已升级；Android/iOS 提供完整、可信的实例清单和实例身份凭据；鸿蒙保留 registry 和精确实例名；身份与总账对应。 |
| 同一安装目录中的 Agent 重启，session ID 变化不会要求重新创建机器。 | `agent-host-id` 与平台运行资料保留；原生实例仍在原位置；不存在竞争 session 或身份冲突。 |
| 普通停止、已有实例重启失败，不应删除原实例数据。 | 使用最终新版本 Manager；正确识别“已有实例”，不把显式删除或换 Agent 当作数据保留操作。已有专项测试验证首次回滚仅作用于本次创建资源。 |
| 新 Server 启动不会因为重建实时设备列表就删除 VM 配置或原生磁盘。 | 使用同一数据库；VM 运行态重置为待重新认领，原绑定/原生身份保留；未完成操作会按约定结束失败，不承诺继续完成。 |
| 总账已删除的旧 ID 不会因为迟到 running 回报变成新配置。 | 使用新 Server；旧 ID 与新 ID 不复用；原生孤儿清理有精确身份依据。 |
| 本次产品修改不需要新增 VM 数据表字段。 | 当前版本比较中 VM 模型未改列，新增操作和宿主身份放在现有 runtime JSON；这不代表旧版本理解新 JSON 语义，也不代表任意数据库版本均已验证。 |

`host_id` 的含义必须写准确：它目前表示 **Agent 安装身份**。持久化文件丢失、路径切换或目录克隆都可能改变或复制它；不能在说明里称作已经验证的物理宿主唯一指纹。

## 3. 升级与回滚矩阵

| 组合或操作 | 独立判断 |
| --- | --- |
| 先升级 Server，旧 Agent 进程暂不重启 | session ID 可保持，运行实例的正向认领有兼容路径；旧停止清单缺完整性标记，可能仍显示待确认，需完成 Agent 升级。旧扫描、停机与超时缺陷仍存在。升级窗口内暂停新的生命周期操作，不代表新能力已全部生效。 |
| Server 就绪后逐台升级 Agent，保留原用户、目录和状态文件 | 推荐顺序；新 Agent 的身份凭据可认回旧行。仍需逐台核对存量 VM ID、原生 ID、状态和数据，不能仅检查 Agent 在线。 |
| 先升级 Agent，旧 Server 保持 452e7d7 | **不允许作为安全升级路径**，已复现 iOS 停止实例误删；Android/Harmony 也没有完整混合二进制现场验收。 |
| 新 Server + 旧 Agent 已重启 | 老停止清单不足以认证事实，不能承诺恢复可用；没有统一版本协商或强制拒绝旧 Agent 的机制，不能作为长期受支持状态。 |
| 更换 storage 路径，未保留 `agent-host-id` | 初审有误删风险；修后已验证保留旧账、不发送自动删除，但不会自动接管。**数据不删不等于自动可用**，需要恢复原安装身份及平台资料。 |
| 同电脑新旧 Agent 同时启动且 storage 不同 | 可能看到同一原生实例；不能据此自动删“副本”。升级流程应避免此重叠，修后仍应拒绝冲突归属。 |
| 把完整 storage 克隆到另一台电脑 | 不受支持，会复制安装身份。当前方案没有硬件指纹校验，不应把目录克隆作为迁移操作。 |
| 只降级 Agent | 已记录 host 身份的配置不能由无 host_id 的新 session 自动认领；不保证恢复可用。 |
| Server 降回 452e7d7 并接受新 session 对账 | 再次暴露 U2；不能作为无条件安全回滚方式。 |
| 回滚数据库到旧快照 | 与代码回滚分开评估；必须先阻止 Agent 对账，核对较新 ID，否则按正常 orphan 规则删除较新原生实例。 |

## 4. 升级操作的必要边界

1. **先结束正在使用的工作。** 停止新增测试派发，等待在跑任务终态，关闭观看会话，等待 VM 启停操作结束；不要把更新 Agent 当作不会中断任务的热更新。
2. **固定同一实例和安装资料。** 记录并保留绝对 `storage_dir`、工作目录、OS 用户、`agent-host-id`；Android 保留原 AVD 路径及数据；iOS 保留原模拟器目录和 `ios_sim_ports.json`；鸿蒙保留 registry、原 `instance_path` 和私有数据。只保留数据库不能恢复原生数据。
3. **Server 先行。** 完成包含升级安全补丁的新 Server 启动与数据库状态核对后，再逐台升级 Agent；确认旧 Agent session 已下线后再启动替代进程，避免两个进程争同一份实例。不要先重启旧 iOS Agent 连接 452e7d7 Server。
4. **核对存量，而不是只测新建。** 对照升级前记录逐台确认 VM ID、AVD/UDID/原生 UUID、运行/停止状态及可恢复的数据样本；有不一致就停在核对，不用“换 Agent”按钮修复归属，因为该按钮按需求会创建新 ID 的空白机器。
5. **身份文件缺失时先保数据。** 不自动改写 owner、不自动删除有账实例；恢复同物理宿主原安装的身份文件和状态资料，再重新连接验证。不要把一个宿主的身份复制给另一宿主。
6. **回滚先做账实核对。** 在允许 Agent 重新对账前确认目标代码和数据库快照包含应保留的 ID；没有这份核对，就不能给出一条“恢复旧库再重启”的通用回滚命令。

已有实例路径还受平台约束：鸿蒙历史非 ASCII 路径会明确报不支持，而不是自动迁移并重建；iOS 端口预留损坏或丢失可能导致 WDA 不可用。保留旧数据与保证升级后立即恢复自动化是两件事。

## 5. 运行中更新不能保证无感

- Agent 进程退出会结束本地异步 Run，`main.py` 的退出路径会停止镜像；可靠上报队列不等同于跨进程保存运行任务。
- Server 的断线回收只把**同一 session ID** 的重连当作原进程仍存活；随机新 session 的旧任务可在宽限期后失败，并按原测试调度策略处理。VM 生命周期“不自动重试”不等于测试批次原有 retry 策略被取消。
- iPad 路径会在正常退出时终止本进程登记的 xcodebuild；不能保证 WDA 和观看会话在 Agent 更新后无中断。
- Android/鸿蒙原生进程能否跨服务管理器重启存活，还受 launchd/Windows 服务及进程组策略影响；源码中没有在 Agent 退出时统一删除实例，不等于已验证所有宿主服务的子进程存活行为。

对应代码：`agent/identity.py:load_host_identity`、`agent/ws_client.py:stable_agent_id`、`agent/main.py:_bootstrap/run`、`agent/drivers/ios_simulator_wda.py:_kill_all_xcodebuild`、`server/ws/agent_ws.py:_reap_disconnected_runs`。

## 6. 说明真实性与未验证项

`execution/RESULT.md` 的三端个人原生用例、截图、回执和清理记录，是已保存的有效证据；但这些用例主要是新建的隔离实例。不能从中推导：

- 已用真正的旧 Server + 旧 Agent 二进制、原数据库和原生存量数据完成整个滚动升级。
- 已证明 Windows、iPad、真实手机或公司部署现场的升级与回滚无损。
- 已验证修改 Agent OS 用户、原生实例根目录、storage 路径或多进程重叠升级后的自动恢复。
- 已验证运行中任务、安装和观看不中断，或 Server/Agent 都能任意次序升级与降级。
- 旧数据库快照可以不核对新实例 ID 就恢复。

原 `final-code-manifest.json` 和个人原生验收属于 74f209d/0e9bde8 对应产品源码；本次升级修复若改变产品代码，需要另列新提交及隔离回归结果，不能继续把旧摘要称为新 HEAD 的完整原生验收。是否补跑原生验收由总控记录，本审查不替代该证据。

## 7. 独立复现与修后验收记录

- 初审：专属测试 `6 failed / 16 passed`。6 个失败是“同机身份变化不应删除有账实例”的安全断言；16 个通过中包含负向边界重放，**不表示所有升级情景安全**。
- 旧 Server 单函数重放：`1 passed`，含一条真实旧代码发出的 Fake Hub 删除指令；这是 U2 风险证据。
- 修后复验：专属独立文件与 Server 负责人升级兼容回归，合计 **54 passed**，见 [修后日志](upgrade-independent-followup.log)。其中 U1 的 6 个初始失败安全断言已通过，U3 的 3 个普通启动竞态已通过。
- 当前代码身份见 [SHA256 快照](upgrade-independent-code-snapshot.json)；产品补丁由 Server 负责人维护，本审查仅新增独立测试和报告。
- **未剩余已复现而未处理的本轮产品 P1；仍不作无条件升级放行。** U2 旧 Server 路径不能安全使用，U4/U5 混合版本及降级不保证可用，U6 数据库回滚必须先核对总账。原生存量滚动升级和运行中更新仍未现场验证。
